# Автотесты PomidorQA

[![CI](https://github.com/<username>/<repo>/actions/workflows/playwright.yml/badge.svg)](https://github.com/<username>/<repo>/actions/workflows/playwright.yml)

Набор автотестов на [PomidorQA](https://aiqa.su/pomidorqa) — сервис 25-минутных встреч для
QA/IT-специалистов: регистрация, профиль с навыками, слоты доступности, каталог участников,
бронирование и отмена встречи.

Продукт тестируется как чёрный ящик: исходного кода приложения у набора нет, доступен только
живой стенд. Поэтому покрытие считается от функциональных требований, а не от строк кода.

## Что проверяет проект

Основной бизнес-риск продукта — встреча, о которой договорились два человека. Она не должна
теряться, дублироваться и доставаться двоим одновременно. Вокруг этого построен набор:

- сквозной путь «зарегистрировался → заполнил профиль → открыл слот → нашёл в каталоге →
  забронировал → увидел встречу у обоих участников»;
- гонка за один слот: подтверждённой остаётся ровно одна бронь;
- освобождение слота после отмены и повторное бронирование другим участником;
- границы роли: гость смотрит каталог, но бронировать не может.

## Архитектура

```
tests/unit/      чистые функции — без сети и браузера
tests/api/       бизнес-правила и HTTP-контракт — без UI
tests/e2e/       пользовательские сценарии в браузере
tests/helpers/   тестовые данные, Arrange через API, cleanup
tests/pages/     Page Object: локаторы и действия одного экрана
docs/            матрица покрытия требований
```

Разделение жёсткое: в spec — сценарий и проверки, в helper — пользователь, в Page Object —
экран. Локаторов в spec нет, `expect` в Page Object нет.

Уровень выбирается по риску, а не по привычке: правила брони дешевле проверять запросом,
а не кликами, поэтому они живут на API-уровне. UI отвечает за то, что человек реально видит.

Оговорка про пирамиду: unit-уровень во внешней автоматизации проверяет собственный код набора,
а не продукт. Широкое основание пирамиды здесь недостижимо, и это осознанный компромисс,
а не недоработка.

## Как запустить

```bash
npm ci
npx playwright install --with-deps chromium

npm run gate        # typecheck → lint → unit → api → e2e
npm run metrics     # сводка метрик по последнему прогону
npm run report      # HTML-отчёт с трейсами упавших шагов
```

Стенд по умолчанию — продакшен. Переопределяется переменной:

```bash
POMIDORQA_BASE_URL=http://localhost:3000 npm run test:e2e
```

## Что проверяет CI

GitHub Actions на каждый Pull Request:

1. `Typecheck and lint` — TypeScript и правила стабильности из `eslint.config.mjs`.
   Браузер не поднимается, пока статика красная.
2. `Playwright tests` — unit, API и E2E на Chromium.
3. Сводка метрик в Summary прогона, HTML/JSON/JUnit отчёты — artifact'ом.
4. `AI Review` — отдельный workflow после зелёного CI. Роль совещательная: ставит
   комментарии, не имеет прав approve и merge.

## Известные дефекты

Расхождения требований и продукта не спрятаны ради зелёного отчёта. Тесты на них написаны
по требованию и помечены `test.fail()`: пока дефект жив, ожидаемый результат — падение,
а когда продукт починят, Playwright сообщит «expected to fail, but passed».

## Роль AI-агентов

В проекте настроены два агента с разными ролями:

- writer пишет и правит тесты по правилам проекта, собирает локаторы по реальному DOM
  и обязан прогнать lint и целевой spec;
- reviewer читает diff в Pull Request и оставляет замечания со ссылкой на правило и строку.

Что агенты не решают: выбор уровня проверки, приоритет по риску, статус расхождения
требований и продукта, approve и merge. Последнее слово за человеком.
